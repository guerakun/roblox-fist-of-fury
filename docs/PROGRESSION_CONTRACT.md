# Progression integration contract

Root owns `ProgressionService.lua`, `ProgressionConfig.lua`, `ProgressionUI.lua` and Bootstrap integration. No dependency from progression back into combat.

- `ProgressionService.Init()` before Combat.Init.
- `GetCombatModifiers(player)` returns damageMultiplier, knockbackMultiplier, moveSpeedBonus, damageReduction. Safe defaults until profile loaded.
- `AwardEncounterClear(players, stageIndex, encounterKind, rewardKey)` grants server-authorized rewards. Stable reward key per campaign/stage/wave prevents repeated grants on checkpoint retry. Types: Wave, Miniboss, Boss.
- `AwardEnemyDefeat(player, enemyKind, encounterKind)` optional small earned rewards; encounter rewards are preferred so support play is not penalized.
- `SetRunState(status, stageIndex)` restricts boon changes to safe intermissions.
- Client `require(script.Parent.ProgressionUI).Init()` once. Separate ScreenGui order30; P/menu opens. MenuOpen player attribute suppresses movement/actions; SettingsOpen remains owned by Main.
- Menu button at anchor(.5,0), position(.5,+54,0,20),96x32; narrow viewport<650 y100.
- `Remotes.Progression` RemoteEvent created by service. Client actions Request, ClaimTier, BuyCosmetic, EquipCosmetic, EquipBoon, PurchasePass. Server packet Snapshot or Notice. Never accept client currency/XP/modifier values.
- Coins can buy fixed-price cosmetic trails/titles. Chapter XP rewards fixed free tiers; premium cosmetics require server-verified pass ownership. Sales disabled with passId0 until experience configuration is complete.
- Guardian: free,8% incoming-damage reduction. Focus:200XP,+8%damage. Haste:400XP,+2movement speed. One boon equipped; no paid upgrades/stacking.


## WO-3.4 district reward ledger (scoped integration passed)

`CampaignRewardBook` owns one journal per user in the current server-authored campaign. Rejoining the same campaign on the same server preserves eligible encounters, consumed keys, immutable district results and actual payment receipts. A new authoritative campaign rotates journals; retired IDs cannot reopen a run. Stale callbacks must recheck the current campaign and journal before mutation. The pending flush captures its campaign ID rather than relabeling old encounters with a later global ID. Published admission remains at most four members; the book rejects a 257th distinct user within one campaign without evicting the previous 256 journals.

`AwardEncounterClear` records that player's nominal eligible base under `campaign:stage:wave`; actual capped payments are tracked separately. `AwardDistrict(player,result)` accepts only a server-produced result with exact campaign/stage identity and valid rank/tier/statistics. The first completion freezes that player's result and bonus calculation. The bonus uses only their eligible nominal base, including a late arrival's smaller total, with rank D/C1.0, B1.15, A1.30, S1.50; difficulty Normal1.0, Hard1.15, Nightmare1.30; and configured earned Heat percentage. These factors multiply. The already-paid encounter base is not paid a second time. District dedupe uses literal `campaign:stage:rank`, never the achieved rank letter.

`GetDistrictReceipt(player,resultId)` returns a current revisioned receipt. `baseCoins/baseXP` are eligible nominal totals; `basePaidCoins/basePaidXP` are actual base payments; `coins/xp` are actual district bonus only. Profile loading overrides status to pending; inability to mutate overrides it to readOnly on every read. Paid/capped values reflect real deltas, including zero at the balance cap. The immutable performance result does not change when pending payments settle. Replayed payments return their original historical receipt and `newlyPaid=false`; aggregate getters provide the current revision, so callers must not replace a newer UI receipt with an older duplicate. Payment-specific deltas drive server run statistics and analytics once.

**Settlement limit:** pending or read-only rewards can settle only while that same campaign remains current and a mutable profile is available. Starting a new campaign discards the old unpaid journal; it does not promise indefinite later payment across restart. This is an explicit fail-closed boundary against stale/retry grants, not durable offline debt storage. A read-only/pending receipt must not be presented as paid or as a guaranteed future grant. Same-campaign reconnect retention is supported; cross-server migration of this in-memory journal and settlement after a new run are not claimed.
