# M4 pickup reward contract — proposed, not implemented

Root preparation during the frozen M3 series,2026-09-24. This resolves a proposed integration shape for WO-4.2; it does not start M4 production work or establish gameplay acceptance. Combat/world/presentation must acknowledge the final contract before source edits. Existing code is `ProgressionService`, `DistrictLedger`, `CampaignRewardBook` and the client `DistrictResultModel`.

## Proposed economy and identity

- One coin bag grants its first eligible claimant **25 earned coins and0 XP**. No party split, paid multiplier, random reroll, rank/Heat/tier multiplication or effect on combat stats. Final placement/count is the separately reviewed34-prop table;25 is a candidate amount, not enabled tuning.
- A stable authored prop ID plus the server campaign ID identifies one drop opportunity. Cosmetic restoration, retry, life replacement, reconnect and same-run world rebuild do not renew it; expiry consumes the opportunity. A new campaign creates a new opportunity. The combat/world registry reserves before any yielding work and never reopens a claimed bag because payment is pending.
- Proposed nonyielding registration API: `Progression.RecordPickupClaim(player, campaignId, stage, propId)`. It is a server callback, **not a remote**. Progression validates the current campaign journal/member and obtains kind/value/authored stage from the trusted drop table; it does not accept client amounts, arbitrary grant keys or a nominated recipient. Combat retains actual touch/life/range/encounter eligibility and atomic winner selection. A callback supplied during Bootstrap avoids introducing a Combat/Progression require cycle.
- Stable prop IDs are at most22 ASCII characters, so a campaign ID of at most130 characters plus `:pickup:` and the prop ID fits the existing160-character composed-key limit. A campaign-wide prop-to-claimant binding must survive removal of the world object; a per-player ledger alone cannot reject the same prop being recorded for another player. The existing PickupRegistry.used boolean is insufficient to retain that winner identity. Bind to the server UserId and current campaign only after all admission checks pass; same-user replay settles the existing record, a different claimant is rejected.
- New claims are allowed only for alive, eligible actors in the authoritative current district while its state is Combat, Intermission or Traverse. They are rejected in Waiting, Advance, Victory, Defeat, travel lock, or a recorded closed district. Check this global campaign/stage/closed-state boundary independently of a particular player having a rank result. Existing recorded claims may settle later; they cannot admit a new claim.
- Preserve the ten-second ground lifetime through same-district wave-clear Intermission/Traverse. Clear leftovers on district close, stage change, retry or run reset. Do not reuse the score-orb service's blanket non-Combat cleanup, which would erase M4 loot prematurely.
- Record the accepted claim synchronously before clearing its world object. The journal uses a distinct key namespace such as `campaign:pickup:propId`; reject unknown/conflicting IDs and mismatched stages. A recorded claim may settle later in the same run, but a late callback cannot record a new claim after its district closes or reopen a rotated campaign.

Registration returns an explicit accepted/duplicate/rejected result and performs no profile save, payment observer or other yielding work. The pickup registry first reserves a candidate; the registration validates both the global winner binding and the player journal atomically, then the registry consumes the object only on accepted/same-winner duplicate. Rejection or a pre-commit exception releases the reservation if the item is still valid and unexpired; stale items are removed without a reward. Commit the binding and journal together after validation, with no yielding callback between them. Schedule payment after accepted registration, using the existing pending-flush path and current-journal checks. Read-only/pending profiles may have a recorded unpaid claim; this must never reopen the item. Do not copy ScorePickupService's current destroy-before-callback ordering blindly.

## Separate receipt accounting

Do not route coin bags through `RecordBounty`: that ledger currently allows one bounty per stage/wave, while multiple props may exist in one wave. Do not add bags to base encounter rewards, because that would multiply loot through the rank/difficulty/Heat bonus. Add a bounded pickup map to the existing per-player campaign journal and an actual-paid `pickupCoins` field to its district receipt. `pickupXP` is unnecessary for the proposed zero-XP item; if a broader field is introduced later, its semantics need explicit review.

Existing immutable rank results stay immutable. The mutable receipt revision advances only when its public payload changes. Settlement status includes recorded but unpaid pickups; `paid` must not appear while a claim is pending/read-only/capacity-blocked. Reuse the existing `paymentState`, current-journal recheck, grant cap, `paid` observer and server analytics path. A `Pickup` economy event uses the same stable payment key and the **actual** awarded delta, once. Capped awards display the cap outcome and cannot reopen the bag for another claimant.

For a completed district, actual coin accounting becomes **basePaidCoins + rank bonus coins + bountyCoins + pickupCoins**. Partial defeats also retain paid incomplete-district earnings. Never compare the sum of completed receipts alone with an entire partial campaign balance. Pickups do not satisfy missing encounter participation or earned tier/Heat completion by themselves. The existing `flushPending` and district settlement paths must include recorded claims without paying a key twice; same-run reconnect uses the existing journal, while real cross-server persistence remains an owner gate.

Presentation adds a distinct **LOOT RECEIVED** line, defaulting absent legacy `pickupCoins` to0. Pending/read-only amounts do not appear as received. The receipt/data model must not calculate rewards from the client snapshot or silently relabel loot as bounty. Space for this line must be tested with the planned short-height/input-mode correction; do not crowd the existing rescue, results or return controls.

## Tests required after implementation

Pure ledger/policy cases: known/stage-matched prop IDs; exact25/0 candidate; repeated/conflicting cross-player claims across different journals and same-user reconnect; composed-key length boundaries; multiple bags in one wave; independent global closed-stage checks including a loot-only player with no rank result; rejected-registration reservation release; Intermission/Traverse lifetime preservation; no rank/tier/Heat multiplication; actual capped grant; profile pending/read-only; current-journal rotation; terminal-record rejection with earlier-record settlement; receipt revision/status; all34 opportunity bound; retry/rebuild/departure/new-run behavior. Re-run the existing reward ledger/profile concurrency suites rather than creating a parallel currency store.

Actual Studio cases must include a real accepted prop break and physical first touch, two-client contention, duplicate limbs, an expired bag, a delayed payment and an actual receipt/balance comparison. Direct API calls alone do not establish physical pickup behavior. Update StyleCampaignAI and the multiplayer receipt observer to include pickupCoins before rerunning the full campaign; their current three-component equality is correct for frozen M3 and must not be altered mid-series. Device and live persistence gates remain separate.

Source hygiene reminder for the future integration: `DistrictLedger.lua` still has an obsolete header describing it as a disconnected draft even though Progression now uses it. Correct that comment when the next authorized production checkpoint opens; the current freeze is unchanged.

No new payment product, purchasable coin, power buff, live storage operation or publishing action is authorized by this proposal. SEC-03 remains open; pickup distance checks do not establish movement-origin authority, and its blocked adversarial fixture remains stopped.
