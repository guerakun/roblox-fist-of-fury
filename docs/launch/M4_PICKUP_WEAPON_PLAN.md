# M4 pickup and weapon handoff — proposed only

Prepared by world during the M2 source freeze at `9f29012`. This is an executable implementation plan, not implemented gameplay or passed evidence. M3 must close its engineering work before M4 starts; root decides release and alone runs Studio, builds, commits and pushes. Missing human, device and published gates remain explicit. No production changes accompany this document.

## Scope and ownership

WO-4.2 includes breakable food, coin bags and weapon drops from the launch feature table, not food alone. Pickups are server-owned, visible to everyone, expire after ten seconds on the ground and go to the first eligible touch. Small food removes 15 percent; large removes 35. WO-4.3 adds exactly three weapon types: pipe, blade and bottle, durability, dropping on accepted hit/launch, and Husk pickup/use. WO-4.1 grabs and WO-4.4 air attacks remain separate required orders; they are not substitutes for these systems.

| Owner | Proposed changes after release |
|---|---|
| world | `DestructionService` accepted-break notification and stable authored prop IDs in `WorldBuilder`; native pickup geometry; enemy-held weapon appearance in `EnemyFactory`; tuning/history docs. |
| combat | Server pickup registry/claims, food and weapon actor state, combat hit/drop integration, Husk pickup state and weapon moves; reuse a common claim primitive with WO-3.5 score orbs if already present. |
| presentation | Hero-held weapon appearance, distinct attack poses/VFX, weapon/durability HUD, pickup feedback and input/readability fixtures. |
| root | Config values, coin grant and dedupe API in ProgressionService, lifecycle integration reviews, all actual Studio/client validation, milestone place build and save. |

New module paths require owner agreement before edits. In particular, world must not add independent combat state to EnemyFactory or directly grant coins from DestructionService. Preserve the current seven queryable core parts and six motors; held visual parts remain noncolliding, nonqueryable and non-touching.

## Existing source constraints

The frozen world has 34 tagged destructible models. Heavy/Special accepted hitbox resolution calls `Destruction.BreakNearby`; the current function only breaks/hides models and emits cosmetic debris. Props restore after twenty seconds; rebuilding destroys the old city, so existing callbacks cannot affect replacement props. There is no gameplay drop hook, pickup service, durability ledger or arbitrary pickup coin grant yet. The new `tests/WorldLifetime.spec.lua` checks all 34 props, debris cap/cleanup and replacement isolation, but is prepared and unrun as of this handoff.

M3 score orbs have a separate five-second lifetime and award score. Keep that distinction when sharing a registry: a breakable coin bag is not a score orb, and food never changes stocks. M3 district-clear healing and One Life stock caps remain authoritative. No Heat contract currently proposes removing food. The movement-authority proposal is not implemented: server distance checks alone must not be advertised as solving SEC-03 client-owned movement origins.

## WO-4.2 implementation sequence

1. **Agree immutable run and drop identity.** The server assigns each authored prop a stable ID independent of Instance identity, and derives a drop key from campaign ID plus prop ID. Record its authored district. A twenty-second cosmetic restore, character replacement, reconnect, checkpoint retry or rebuilding the same run cannot replenish a consumed drop budget. A genuinely new campaign ID resets it. Keep this gameplay ledger outside world Instances so a rebuild cannot erase it. One drop budget per prop per campaign is the proposed anti-farming rule; expired drops also consume their budget. Write the final rule and distribution into COMBAT before implementation.
2. **Add one accepted-break hook.** Set Broken first, perform the existing visual break, then notify a server callback with trusted assembly identity and floor position. Supply the current accepted attacker/run/encounter context through Combat's call, not a client payload. Reject nonfinite input, old-world assemblies and breaks outside the active district/arena before producing gameplay drops. Cosmetics may retain their current radius behavior. The callback must not yield inside the break loop and must be safe when unset, preserving existing fixtures. Prevent a callback exception from leaving a half-restored model or duplicating a reserved drop.
3. **Author a deterministic, inspectable drop table.** Map all 34 prop IDs to one entry or an explicit no-drop entry, with food, coin bags and all three weapon types represented across the three districts. Choose amounts and frequency with combat/root against M3 survival pressure; do not silently reuse generic random debris as loot. Keep a fixed campaign table across retries, rather than rerolling for large food or coins. Use a new pure table/schema spec and record actual counts per district before root approves the work-order checkpoint.
4. **Create the server registry and shared visuals.** Each record contains a unique ID, run/stage/encounter generation, kind, trusted payload, ground position, expiry, claim state and visual reference. Native anchored geometry at a clamped reachable floor point is sufficient; no new external asset dependency is needed. All clients see one replicated object. A server touch trigger proposes a candidate; validation checks current actor identity/life, alive/non-downed state, run/stage, no travel lock, actual bounded position and unexpired record. A bounded server overlap check may supplement missed physics touches using the same claim function. Clients never provide amounts, weapon IDs, durability, positions or grant keys.
5. **Claim without a race.** Before any yield, mark a valid available item reserved/claimed and record its claimant. Duplicate limb touches, player-player and player-Husk races cannot award twice. Food applies synchronously to the current life, clamped at zero; proposed eligibility excludes an actor already at zero percent so it can remain for an injured teammate. Food is player-only; coin bags are player-only; Husk competes only for weapons. Coin grants can yield/fail, so a reserved bag becomes a pending server grant with the same stable key; never reopen it to another claimant after an ambiguous write. Root supplies a deduplicated grant/receipt path and a visible pending/read-only outcome. A first claimant leaving does not transfer an already reserved coin grant to someone else.
6. **Clean up every lifecycle.** Ten seconds means server elapsed time from ground spawn, with expiry checked again at claim. Destroy visuals and disconnect touch callbacks on claim, expiry, stage travel, retry, world replacement, run end and clear. Invalidate old delayed callbacks with record/run generation checks. Clearing visuals does not clear campaign consumption keys. Unclaimed drops are not carried into a retry; held weapon handling is defined below. Confirm a bounded live-record count from the authored drop budget plus active weapon drops and remove expired registry entries, not only their Instances.

Shared visibility does not imply a shared award: first eligible touch receives the food, coins or weapon. This is the launch-plan rule; do not introduce personal copies or silent equal party payments. Distinct silhouettes, labels and colors should let the party identify food versus money versus a weapon without relying solely on color.

## WO-4.3 implementation sequence

1. **Define three data profiles.** Pipe is a blunt reach swing, blade a narrower cutting swing, bottle a short single-use smash. This is a proposed melee interpretation; ranged bottle throwing is not required by the launch work order and must be explicitly agreed if chosen. Starting durability proposal: pipe five accepted swings, blade four, bottle one. Combat/root must set and document damage/range/windup/knockback values relative to ordinary Light before implementation; no implied final balance numbers exist here. Heavy and Special retain hero identity. An accepted weapon Light consumes one durability even on a miss, avoiding unlimited free probing; rejected inputs consume none. Durability exhaustion removes the held item after its captured strike resolves, so the last legal swing still works. If a hit/KO cancels that final pending strike, destroy the exhausted record; never emit a zero-durability ground pickup.
2. **Use one authoritative weapon identity.** A record moves among ground, held by one player/Husk, pending captured attack, exhausted and destroyed states. Transfer existing remaining durability; never mint a fresh full weapon on every drop. One held weapon per actor; proposed auto-pickup refuses another weapon while occupied instead of repeatedly swapping both on contact. Proposed snapshot is `weapon={id,kind,durability}` or explicit `false`; presentation must clear mounts on server false and character/life replacement rather than infer removal from a local counter. Attack FX carries the captured weapon kind/record ID/attack serial so a final swing can render without retaining a stale held mount after transfer. Final event fields require combat/presentation agreement. Replicated attributes/snapshot describe state, not entitlement. Capture record ID, actor life and attack serial so ownership changes cannot let an old delayed strike resolve from a new holder.
3. **Drop through accepted combat transitions.** An accepted unguarded damaging hit or actual launch drops the held record once; an immune/rejected hit does not. Proposed blocked-chip interpretation: a guarded chip without launch keeps the weapon, but an actual physical launch disarms even if the hit was guarded. A successful perfect block does not drop it. Dropping cancels any pending weapon strike whose actor/state is invalid; no duplicate drop from the same hit-plus-launch chain. Use a reachable floor point and a short documented former-holder repickup lock so immediate overlap cannot undo disarm. A fresh ground drop gets a ten-second expiry; this never restores durability. Death, downed, departure, character replacement, stage travel, retry and terminal run clear need explicit handling: proposed rule clears held weapons on travel/retry and drops them on a combat KO in the still-active encounter. Retain this as a deliberate documented rule, not an accidental reset side effect.
4. **Integrate Husk fairly.** Only a living, free Husk with no weapon may seek a reachable current-encounter ground weapon. It releases an unused attack token while walking to PickUp, and competes through the same atomic claim function. Never teleport to loot or bypass camera-safe movement. Failed/expired claims return to normal AI. Armed attacks still require director capacity, at least .30 seconds of tell, camera checks at attack/impact, existing cancel behavior and server hitboxes. Keep each archetype's required normal behaviors; armed Husk is an additional contextual option, not a way to suppress the two-action measurement gate. Add appropriate Body tell/pose/flash for weapon swings.
5. **Finish appearance and controls.** World authors three low-part weapon silhouettes and welded enemy-hand mounts. Presentation adds hero mounts without modifying queryable cores or weapon collision hitboxes, displays remaining durability and a short disarm/expiry cue. Automatic touch pickup and weapon Light reuse existing keyboard, controller and touch inputs; this still requires actual reachability/readability checks on each input surface. Any manual throw/drop extension would require its own approved mapping and tests rather than silently adding a desktop-only action. Reuse reviewed Toolbox pose/VFX sources where suitable and record any new assets before importing.

Every order follows implement → scoped test → different-owner review → fix → root commit/push. Prefer a shared integration checkpoint that avoids presenting inert loot to players. No v1.1 content is added to fill waiting time.

## Explicit unresolved and blocked items

- All production work is blocked by the current M2 freeze and M3 dependency, not by owner permission. Combat independently reviewed this plan as a proposed contract and passed it after clarifying exhausted-strike cancellation and guarded-launch disarm. Presentation independently passed the proposed visual/input scope; its snapshot and captured-attack FX contract requirement is retained above. Neither review is runtime evidence.
- Exact drop distribution/coin values, weapon combat values, pickup radius and repickup lock require the named owners' source-level agreement and tuning documentation. Proposed choices above keep work executable without waking the owner.
- Root must provide the M3 run identity, actor eligibility and root reward grant APIs before integration; do not duplicate them in world code.
- Actual new Studio tests, shared visuals, screenshots/clips, physical touch/gamepad checks and M3 before/after measurements have not run. The existing blank world capture limitation may still block visual evidence and must be reported if it persists.
- SEC-03 origin hardening is a separate documented source gap. These pickup validation checks cannot turn an unimplemented movement validator into a verified security claim.

## Preserved alternatives

Personal loot copies, equal party splitting, manual weapon swap/drop, a ranged bottle and variable drop rerolls are design alternatives, not current launch commitments. They are preserved here so choosing the bounded first-touch melee design does not erase the ideas. Survival/boss rush and other v1.1 content remain outside this work order.
